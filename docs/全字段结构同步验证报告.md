# 全字段结构同步验证报告

日期：2026-10-28。

## 本次需求与行为

按用户最新要求，每个真实字段差异都生成对应同步语句，将目标字段调整为源定义：缺字段使用 `ADD`，多余字段使用 `DROP COLUMN`，类型、长度、精度、小数位和可空性不同使用 `MODIFY`。源可空、目标非空时也直接给出 `NULL`；反向差异给出 `NOT NULL`，不再因历史数据或非空约束放宽而只给注释。

同库归档以源物理字段为准；迁移以源查询结果映射为目标数据库方言的字段定义为准。目标容量更宽也属于定义差异。主键、索引、默认值、注释等完整 DDL 属性仍不在当前字段比对范围；元数据不足不能虚构定义，同一物理目标的源定义互相矛盾时列出冲突候选，避免相互覆盖。

建议直接给出 `ALTER TABLE`，不分析历史行数据后再决定是否生成。执行前仍由用户人工审核并二次确认；脚本执行后不自动启动业务数据任务，失败即停且不重试。

## 截图对应场景

| 场景 | 本次处理 |
|---|---|
| `PROF_TYPE CHAR(1)` 源可空、目标非空 | 生成对应 `MODIFY ... CHAR(1) NULL` |
| `TENANT_ID VARCHAR(32)`、`USER_OID VARCHAR(100)` 仅可空性不同 | 各自生成独立 `MODIFY ... NULL`，不因类型长度相同而遗漏 |
| 源 `NOT NULL`、目标可空 | 按源定义给出 `MODIFY ... NOT NULL` |
| 类型、长度、数值精度或小数位不同 | 均生成源定义的 `MODIFY`，包括目标更宽的情况 |
| 源字段缺失 / 目标字段多余 | 分别生成 `ADD` / `DROP COLUMN` |
| Oracle 查询 `NUMBER(0,-127)` 对物理 `NUMBER(p,s)` | 只把这类查询元数据视为精度未指定；不把未知查询精度当成真实表结构差异 |

Oracle 官方 [JDBC 19c 元数据说明](https://docs.oracle.com/en/database/oracle/oracle-database/19/jajdb/oracle/jdbc/OracleResultSetMetaData.html#isVariableScale-int-) 指出，小数位未指定时返回 `-127`。代码通过共享 `ArchiveQueryMetadataSupport` 在汇总预检和 `ArchiveEngine.prepare` 最终查询校验中统一处理，限定于 Oracle 原生 `NUMBER`、查询精度 0、小数位 -127；已知类型和已知精度错误仍拒绝。物理表元数据直接读取，源/归档物理字段继续严格比较。

## 单文件与离线检查

Java 文件按依赖顺序逐个执行 JDK 8 `javac -encoding UTF-8 -source 8 -target 8 -implicit:none`，输出到忽略目录 `target/field-alignment-check`；未使用 Maven 编译或重新打包。依赖复用既有交付 Jar。

- 归档回归：MySQL、Oracle、DM 的 `NULL/NOT NULL` 双向变化、纯约束差异与合并长度差异、额外字段删除、原生类型还原、全表汇总、父失败子继续、无写入/删除。
- Oracle 查询回归：完整两阶段准备流程兼容未知精度和查询可空性；已知 precision、scale、JDBC 类型、原生类型错误仍拒绝，其他数据库不套用 Oracle 规则，查询兼容不掩盖物理字段差异。
- 迁移回归：字段定义双向对齐、同库整数原生类型、跨库映射、缺字段与额外字段、同目标别名及跨步骤冲突、源可空性不明确的处理。
- 执行回归：允许任务生成的单列 `DROP COLUMN`，保留目标表、确认、摘要、单次执行检查；仍拒绝 `DROP TABLE`、删约束、任意多操作拼接和 DML。
- 原有数字兼容、归档图和达梦 SQL 定向回归保持验证。

最终统一运行 `ArchiveStructureValidationCheck`、`StructureValidationAggregationCheck`、`StructureSyncExecutionCheck`、`NumericCompatibilityCheck`、`ArchiveGraphValidationCheck`、`DamengSqlCompatibilityCheck` 六项均通过。迁移回归另覆盖 BOOLEAN 跨库映射及 CLOB→LONGTEXT 的回读一致性，MySQL `FLOAT/DOUBLE` 的驱动 `scale=31` 不拼成非法 `(M,D)`，真实有效的 `FLOAT(10,2)` 仍保留。

## 真实 MySQL 验证

使用用户此前提供的测试数据库。入口为 `StructureSyncMysqlIntegrationCheck`，连接信息从环境及标准输入读取；单次真实登录、关闭自动重连，只操作本轮 `LDM_SE_<时间戳>` 隔离表。公开执行服务经记录代理复用唯一真实连接，确认、摘要、目标核对、占用及实际 JDBC 执行均走生产代码。

新增迁移和归档各一组完整字段对齐测试，每组构造十项差异：三个纯非空放宽、一个非空收紧、一个文本容量缩小、一个数字精度/小数位缩小、一个类型改变、一个缺失字段、一个多余字段，以及一项 `FLOAT/DOUBLE` 类型差异。逐项检查十个字段都出现在可执行 `ALTER TABLE` 中，再执行全部语句；核对 `information_schema.columns` 的字段集合、原生 `COLUMN_TYPE` 和 `IS_NULLABLE` 与源表逐项一致，并重新调用生产预检确认没有残余差异。

真实结果：两组各十条同步语句全部成功，源/目标字段定义比较一致，重新预检通过；本轮共创建十张隔离表，均已清理，残留为 0。

既有迁移/归档两条建议成功、未确认拒绝、重复拒绝、部分失败保留计数和不自动启动业务任务的场景同时验证。所有应用侧 SQL、元数据 API、逻辑连接关闭及清理顺序见[完整实测 SQL 记录](全字段结构同步实测SQL记录.md)。本轮预检及 DDL 无绑定参数；驱动内部登录初始化及元数据内部 SQL 无法从应用代理获取原文，记录明确说明。
